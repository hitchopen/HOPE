# Published `model_21800`

For the current public Runner package, Xbox controls and Kernel Mode, see
[Runtime operation](operations/runtime_xbox.md) and its
[validation limits](operations/runtime_public_validation.md).

This repository includes the complete public model bundle used by the build_1
`hitter_pure` deployment line:

| Artifact | Repository path | Purpose |
| --- | --- | --- |
| Training checkpoint | `hope_training/whole_body_tracking/checkpoints/model_21800.pt` | Warm-start/play checkpoint at iteration 21800. |
| Deploy actor | `a3_deploy/a3_deploy_example/models/model_21800/policy/exported/policy.onnx` | The 110-D observation, 31-D action actor used by the deploy runner. |
| Deploy parameters | `a3_deploy/a3_deploy_example/models/model_21800/policy/params/deploy.yaml` | Joint order, action offsets/scales/clips, timing, and PD constants for this actor. |
| Gate 3 video | [`assets/model_21800_gate3_mujoco.mp4`](assets/model_21800_gate3_mujoco.mp4) | build_1 Planner + policy-native Runner closed loop in the AimRT MuJoCo viewer. |

The ONNX and `deploy.yaml` are the deploy artifacts used by the native build_1
runner. The public checkpoint preserves the model weights, optimizer state and
`iter: 21800` exactly. Machine-bound 6144-environment resume state, private
absolute paths and W&B run identity were removed; it is therefore a standard
warm-start checkpoint, not a byte-identical continuation of the original
machine process.

The supported production Planner is now exclusively the ROS 2 C++ package
`hope_planner_cpp`. The retired `hope_planner` runtime is not part of the
current build, launch or hardware procedure. Python remains in this repository
only where it is required by ROS build tooling, offline tests, data conversion
or standalone evaluation; it is not the production Planner implementation.

## Run the deployed actor in MuJoCo

From a fresh clone, only a normal Python virtual environment is required:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r a3_deploy/a3_deploy_example/reference/requirements.txt

# Headless contract smoke. The default config selects model_21800.
a3_deploy/a3_deploy_example/scripts/run_pingpong_sim.sh --duration 10

# Interactive window at the deployment control rate.
a3_deploy/a3_deploy_example/scripts/run_pingpong_sim.sh --view --realtime
```

The actor has two inputs (`obs[1,110]`, `time_step[1,1]`) and an
`actions[1,31]` output. The public wrapper derives the reference clock from the
current command, translates between the training and SDK joint orders, and
loads the model's exported action and PD arrays. Compact single-input public
exports remain supported through `--onnx`.

The standalone real-ball evaluator remains available for focused policy checks:

```bash
MUJOCO_GL=egl python hope_training/whole_body_tracking/scripts/mujoco_eval_onnx.py \
  --eval-mode independent --num-serves 4 --max-trial-seconds 1.8 --seed 0
```

## Gate 3 closed-loop video

The committed video was recorded from build_1's Gate 3 qualification and the
published model_21800 policy directory. It is not the standalone evaluator
above. The current Gate 3 entry retains that 12-ball scenario and model bundle,
while running the updated public Runner and relay. It uses the same C++
packetizer/Planner topology as hardware:

```text
physical MuJoCo ball -> simulated OptiTrack -> production relay -> Planner
-> schema-2 command -> policy-native C++ runner -> AimRT MuJoCo plant
```

The runner entered MOTION once and was not reset between shots. Gate 3 invokes
the x86-only `--gate3-qdes-audit-only` option: finite `q_des` is published
unchanged, and `q_des` or measured actual-q limit excesses are recorded as
telemetry instead of terminating the runner. The production default is
unchanged when this explicit Gate 3 option is absent.

The video documents the complete 12-serve Gate 3 execution path. For a current
run, use the reports produced by the command below as the source of contact,
landing, robot-state and qualification results; the recorded video is a visual
runtime reference rather than a reusable verdict.

## What the current Gate 3 test validates

There are three separate checks in this public branch:

| Check | Entry point under `a3_deploy/a3_deploy_example/scripts/` | Evidence |
| --- | --- | --- |
| Gate3 environment preflight | `pp_gate3_hitter_pingpong.sh --preflight-only` | Package, installed workspace, simulator and scenario dependencies; starts no runtime nodes |
| Physical-ball Gate3 | `pp_gate3_hitter_pingpong.sh` | Autonomous Planner/Runner execution, ball contact/landing and plant reports |
| Serve / Ready transition regression | `validate_serve_loop_mujoco.py` | Native controller transitions and floating-base balance; no physical ball, ROS or full Runner process |

The public runtime update passed **28 transition cases / 200 serve cycles**,
including Normal Play re-entry 0.1 s into Ready. That result is documented in
[Public runtime validation](operations/runtime_public_validation.md). The full
physical-ball Gate3 run has **not been rerun for this runtime update**; neither
the transition result nor the historical video supplies a current Gate3 verdict.

Kernel Mode's local IMU/stance odometry is for controller testing without
OptiTrack. Physical-ball Gate3 uses the Normal Play localization/Planner path,
with simulated mocap supplied to the production relay. Do not add `--kernel-mode`
or replace that relay with a fabricated hardware pose to claim a Gate3 result.


The formal Gate 3 entry is an x86 MuJoCo closed loop, not an Isaac replay and
not a direct `torch.load()` of the checkpoint. `model_21800.pt` is the training
artifact; deployment runs its exported actor,
`models/model_21800/policy/exported/policy.onnx`, through the native C++ Runner.
The package builder verifies that the ONNX SHA-256 matches
`params/deploy.yaml` before it permits a Gate 3 run. Loading the `.pt` directly
is covered separately by the Isaac Lab command above.

Gate 3 exercises the complete runtime chain:

```text
MuJoCo physical ball/table/racket
  -> simulated OptiTrack and production relay
  -> Planner schema-2 command
  -> model_21800 policy-native C++ Runner
  -> AimRT MuJoCo robot plant
  -> measured contact, landing, plant and Runner reports
```

The profile is build_1's original 12-ball qualification sweep. The launcher
uses the original `[-3.0, 0.0, 2.2] m/s` feed and six forehand plus six backhand
lateral positions. Each ball remains side-neutral at the launcher: the
production C++ Planner selects forehand or backhand from live geometry. The
Runner enters MOTION once and is not reset or rescued between serves.

The explicit x86-only `--gate3-qdes-audit-only` option records finite actor
commands without clipping them so policy behavior remains observable. A
non-finite final `q_des` or measured joint state still terminates the Runner.
This option is not enabled by normal hardware launchers.

## Build the current native Runner, C++ Planner and MuJoCo components

The commands in this section run on an x86_64 development laptop. They use the
`hope` distrobox because ROS 2 Jazzy is not expected to be installed on the
host. Run each block from the host shell; blocks that need ROS/native
dependencies enter the distrobox explicitly, while the source-contract tests
remain host-only.

### 0. Reproduce the `hope` environment on a new machine

Complete the host prerequisites, clone and `hope` container installation in
[`DISTROBOX_SETUP.md`](DISTROBOX_SETUP.md). That guide is the canonical,
working-machine-derived setup and records both environments:

- `grasping`: the digest-pinned Isaac/PyTorch training environment;
- `hope`: Ubuntu 24.04, ROS 2 Jazzy and the native C++/MuJoCo build tools used
  by this section.

Only `hope` is used below. Do not build this ROS/native path in `grasping`,
and do not install a second ROS distribution on the host. The canonical clone
location is `$HOME/workspace/HOPE`; if a different host-home path was chosen,
set `HOPE_ROOT` to that clone consistently.

Validate the completed container from the host:

```bash
cd "$HOME/workspace/HOPE"
export HOPE_ROOT="$PWD"

distrobox enter hope -- env HOPE_ROOT="$HOPE_ROOT" bash -lc '
  set -eo pipefail
  source /opt/ros/jazzy/setup.bash
  test -e "$HOPE_ROOT/.git"
  test "$(uname -m)" = x86_64
  test "$ROS_DISTRO" = jazzy
  test "$(. /etc/os-release && echo "$VERSION_ID")" = 24.04
  ros2 --help >/dev/null
  cmake --version
  echo "hope native-build environment: READY"
'
```

For a GUI Gate 3 run, also confirm `DISPLAY` or `WAYLAND_DISPLAY` is present
inside `hope` and that `xdpyinfo` succeeds. Headless runs use `PP_VIEWER=0`.

The native laptop path below is x86_64, not a Rockchip/MDU cross-compile.
`setup_a3_env.sh` downloads the public Unitree SDK2 2.0.0 x86 libraries and
ONNX Runtime into ignored `thirdparty` paths on the first run. A fresh clone
therefore still needs network access or a populated download cache.

### 2. Build the ROS transport and C++ Planner workspace

```bash
cd "$HOME/workspace/HOPE"
export HOPE_ROOT="$PWD"

distrobox enter hope -- env HOPE_ROOT="$HOPE_ROOT" bash -lc '
  set -eo pipefail
  source /opt/ros/jazzy/setup.bash
  cd "$HOPE_ROOT/hope_ws"

  rosdep install \
    --from-paths src \
    --ignore-src \
    --rosdistro jazzy \
    -y

  colcon build \
    --symlink-install \
    --base-paths src ../NatNet2ROS2/src/motion_capture_tracking_interfaces \
    --packages-select motion_capture_tracking_interfaces hope_msgs hope_bringup hope_planner_cpp \
    --cmake-args \
      -DBUILD_TESTING=OFF \
      -DCMAKE_BUILD_TYPE=Release \
      -DPython3_EXECUTABLE=/usr/bin/python3 \
      -DPYTHON_EXECUTABLE=/usr/bin/python3

  source install/local_setup.bash
  /usr/bin/python3 -c "from motion_capture_tracking_interfaces.msg import NamedPoseArrayV2"

  test "$(ros2 pkg prefix hope_planner_cpp)" = \
    "$HOPE_ROOT/hope_ws/install/hope_planner_cpp"
  test -x \
    install/hope_planner_cpp/lib/hope_planner_cpp/hope_planner_cpp_node
  test -x \
    install/hope_planner_cpp/lib/hope_planner_cpp/hope_ball_flight_packetizer
  ros2 launch hope_planner_cpp model21800_hardware.xml --show-args >/dev/null

  echo "C++ Planner build and launch metadata: READY"
'
```

The two executables above are the current runtime pair: the Laptop-side
`hope_ball_flight_packetizer` freezes an incoming flight into
`/ball/flight_packet`, and the HDU-side `hope_planner_cpp_node` consumes that
packet and publishes the schema-2 racket command. Do not substitute the retired
`hope_planner` package. The explicit `/usr/bin/python3` settings keep Jazzy's
rosidl message generator on Ubuntu's Python 3.12 when a user-level Python 3.10
is earlier on `PATH`; they do not make the Planner a Python runtime.

The additional `motion_capture_tracking_interfaces` package supplies
`NamedPoseArrayV2` for Gate3's `/optitrack/poses` boundary, including source
headers. The simulator publishes `UCB_P1`, `PPT` and the active `Ball` through this
message. Building these interfaces does not start or require physical OptiTrack.
After updating the branch, rebuild both `motion_capture_tracking_interfaces` and
`hope_bringup`; an older install that only supplies V1 is insufficient.

### 6. Validate the Gate 3 environment without starting runtime processes

The default calibration is generated by `pp_gate3_sim_calibration.py` at
`/tmp/hope-gate3-sim-calibration.json`. It carries `simulation_only: true`,
`source.kind: mujoco`, the public 24-sticker `stickers_v3` layout metadata and
an identity `UCB_P1`-to-pelvis transform for the P1 simulation. The simulated
mocap publisher and production relay consume the same receipt. It is not a
measured venue calibration and must not be installed as a robot's field receipt.

For a custom simulation transform, set `PP_P1_CALIBRATION_RECEIPT` to its existing
JSON path. This suppresses default generation, so the selected file must be
readable and compatible with the relay's layout/transform contract. Leave the
variable unset for the standard public test. Main's uncalibrated field config
is not a reason to copy a private robot calibration into this test.

Preflight starts no Runner, Planner, ROS node or MuJoCo process, but it does write
local files: it regenerates the default simulation receipt and Planner evidence,
and removes the previous physical-ball report. Archive any `/tmp/pp_*` results
that you need before invoking preflight or a new run.


```bash
cd "$HOME/workspace/HOPE"
export HOPE_ROOT="$PWD"

distrobox enter hope -- env HOPE_ROOT="$HOPE_ROOT" bash -lc '
  set -eo pipefail
  source /opt/ros/jazzy/setup.bash
  source "$HOPE_ROOT/hope_ws/install/local_setup.bash"
  /usr/bin/python3 -c "from motion_capture_tracking_interfaces.msg import NamedPoseArrayV2"
  export PP_DIST="$HOPE_ROOT/a3_deploy/a3_deploy_example/dist/a3_deploy_x86_64"
```

Success ends with `PREFLIGHT PASS` and `G3_HITTER_PINGPONG_RC=0`. The output
must identify `hope_ball_flight_packetizer` and `hope_planner_cpp_node` under

### 7. Run the public Gate3 physical-ball scenario

Run this only in a dedicated `hope` distrobox session with no other MuJoCo,
Runner, Planner or iceoryx session active. The launcher's startup/exit cleanup
uses process-name matching and removes iceoryx shared-memory files; a different
ROS domain alone does not isolate that cleanup. It also overwrites the fixed
`/tmp/pp_*` reports. The entrypoint starts this chain:

```text
simulated OptiTrack -> hope_ball_flight_packetizer -> /ball/flight_packet
  -> hope_planner_cpp_node -> /racket/command_flat
  -> model_21800 policy-native C++ Runner -> AimRT MuJoCo plant
```

With the interactive MuJoCo window:

```bash
cd "$HOME/workspace/HOPE"
export HOPE_ROOT="$PWD"

distrobox enter hope -- env \
  HOPE_ROOT="$HOPE_ROOT" \
  PP_VIEWER=1 \
  bash -lc '
  set -eo pipefail
  source /opt/ros/jazzy/setup.bash

  export PP_SIM_INSTALL="$HOPE_ROOT/a3_deploy/A3_MuJoCo_Sim/aimrt_mujoco_sim/cmake-build-model21800-gate3/install"
  cd "$HOPE_ROOT"
  bash a3_deploy/a3_deploy_example/scripts/pp_gate3_hitter_pingpong.sh
'
```

The launcher runs the original 12-shot lateral sweep: six forehand and six
backhand positions with initial ball velocity `[-3.0, 0.0, 2.2] m/s`. The
launcher does not command the hitting side; the production C++ Planner selects
it from each live flight packet. The Runner enters MOTION once and remains in
the continuous closed loop without a per-serve reset or recovery shortcut.
Contact, legal landing, actual robot motion and all final verdict fields are
measured at runtime.

For a headless run, use the same command with `PP_VIEWER=0`. The authoritative
outputs are:

| Output | Meaning |
| --- | --- |
| `/tmp/pp_rally_report.json` | Per-serve and final Runner/Planner verdict. |
| `/tmp/pp_physical_ball_report.json` | Measured contacts and legal landings. |
| `/tmp/pp_mujoco_plant_report.json` | Plant timing, state and command evidence. |
| `/tmp/pp_obs.csv` | Per-tick actor observation audit. |
| `/tmp/pp_runner_trace.csv` | Runner state/command trace. |
| `/tmp/pp_runner.log` | Native Runner log and transitions. |
| `/tmp/pp_planner_envelope_report.json` | Scenario/Planner contract preflight evidence. |
| `/tmp/pp_mujoco_plant.csv` | Measured plant and actuator trace used by the plant scorer. |
| `/tmp/pp_planner_debug.csv` and `/tmp/pp_flight_packets.csv` | Planner decisions and packetizer flight inputs. |
| `/tmp/hope-gate3-sim-calibration.json` | Default simulation-only localization provenance. |

Read the final `G3_HITTER_PINGPONG_RC` together with all three reports. The
conductor writes `runner_gate_pass`, `planner_contract_pass`, `physical_ball_pass`
and `certification_pass` in `pp_rally_report.json`; the wrapper subsequently runs
the plant and observation/phase scorers, which can still fail the overall run.
Do not treat the conductor's result alone as the final exit status.

The wrapper selects 12 engaged and completed serves, no rescues, at least 11
contacts and 10 legal landings overall, and per-side coverage requirements.
Idle behavior and plant evidence are also checked. Inspect the measured counts,
recovery, falls, missing evidence and scorer failures; a window opening, one
successful contact or a zero-fall subset is not a complete pass. The JSON field
name `certification_pass` is a simulation scorer result, not real-robot or venue
certification. Archive the logs, reports and selected calibration with the
commit and model identity before another invocation overwrites them.

### 8. Startup troubleshooting

- `NamedPoseArrayV2` import failures or no `/optitrack/poses` output require the
  updated interface build from step 2. Source the selected workspace in the same
  shell; a successful V1 import alone does not validate the new boundary.
- `installed hope_world launch/config is stale or missing` requires rebuilding
  `hope_bringup`. Gate3 compares the source and installed launch/config bytes.
- A missing custom simulation receipt means `PP_P1_CALIBRATION_RECEIPT` points
  at an absent file. Correct it or unset it to use the generated default.
- To use nonstandard build locations, set `PP_DIST`, `PP_SIM_INSTALL` and
  `PP_HOPE_WS` explicitly. The latter must have `src/` and `install/` beneath it;
  it is not the path to an install directory alone.

- `runtime config missing: .../dist/a3_deploy_x86_64/...` means the native x86
  package in step 3 has not been produced. It does not mean that the user must
  cross-compile for Rockchip.
- A missing `libaimrt_iceoryx_plugin.so` or `libaimrt_ros2_plugin.so` means the
  native package is incomplete. Re-run step 3 from a clean current checkout;
  the public runtime builder includes the required runtime-loaded plugin targets.
- `PREFLIGHT PASS` proves dependencies and C++ topology only. Run step 7 to
  produce contact, landing and Runner/plant measurements.
- A MuJoCo window requires a working host display socket. Confirm it with
  `distrobox enter hope -- xdpyinfo >/dev/null`; otherwise use `PP_VIEWER=0`.

## Native Runner and C++ Planner reference

The model directory already has the layout consumed by the build_1 C++ runner:

```text
models/model_21800/policy/
├── exported/policy.onnx
└── params/deploy.yaml
```

After building `a3_deploy_onnx_ref_pingpong`, select the public
transport/runtime config and pass that directory as `--policy-dir`:

```bash
cd a3_deploy/a3_deploy_example
source setup_a3_env.sh
cmake -S . -B build
cmake --build build --target a3_deploy_onnx_ref_pingpong -j

# The source-tree build writes the executable under dist/. Start in PASSIVE;
# --planner selects the schema-2 command input published by the C++ Planner.
dist/a3_deploy_x86_64/a3_deploy_onnx_ref_pingpong \
  --runtime-cfg src/a3/a3_deploy_onnx_ref/config/a3_runtime_config.pingpong.hitter_pingpong.yaml \
  --policy-dir models/model_21800/policy --planner --policy-native \
  --start passive --official-stand
```

The supported Planner process is the C++ node below. Its production input is
the immutable `/ball/flight_packet` published by
`hope_ball_flight_packetizer`:

```bash
source /opt/ros/jazzy/setup.bash
source hope_ws/install/local_setup.bash

ros2 launch hope_planner_cpp model21800_hardware.xml
```

The Planner and Runner normally execute on different machines in the hardware
topology; this command is the Planner identity reference, not an instruction to
co-locate both processes.

That is the public equivalent of the model selection in the build_1 field
procedure; site addresses, operator login details and session logs are
deliberately not published. The source Runner, C++ Planner and model bundle are
open, while actual A3 motor I/O still requires the separately licensed AgiBot
vendor runtime. Operators must retain their vendor e-stop, limits and hardware
procedure; this document does not auto-start motion or bypass robot protections.

The source and published model artifacts are released under the repository
license. AgiBot-provided files retain the notices and licensing stated in
[`A3_ASSETS.md`](../A3_ASSETS.md).
