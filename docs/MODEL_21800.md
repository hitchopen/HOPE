# Published `model_21800`

This repository includes the complete public model bundle used by the build_1
`hitter_pure` deployment line:

| Artifact | Repository path | Purpose |
| --- | --- | --- |
| Training checkpoint | `hope_training/whole_body_tracking/checkpoints/model_21800.pt` | Warm-start/play checkpoint at iteration 21800. |
| Deploy actor | `a3_deploy/a3_deploy_example/models/model_21800/policy/exported/policy.onnx` | The 110-D observation, 31-D action actor used by the deploy runner. |
| Deploy parameters | `a3_deploy/a3_deploy_example/models/model_21800/policy/params/deploy.yaml` | Joint order, action offsets/scales/clips, timing, and PD constants for this actor. |
| Gate 3 video | [`assets/model_21800_gate3_mujoco.mp4`](assets/model_21800_gate3_mujoco.mp4) | build_1 Planner + policy-native Runner closed loop in the AimRT MuJoCo viewer. |

The ONNX and `deploy.yaml` are the deploy artifacts used by the native build_1
runner. The public checkpoint preserves the model weights, optimizer state and
`iter: 21800` exactly. Machine-bound 6144-environment resume state, private
absolute paths and W&B run identity were removed; it is therefore a standard
warm-start checkpoint, not a byte-identical continuation of the original
machine process.

The supported production Planner is now exclusively the ROS 2 C++ package
`hope_planner_cpp`. The retired `hope_planner` runtime is not part of the
current build, launch or hardware procedure. Python remains in this repository
only where it is required by ROS build tooling, offline tests, data conversion
or standalone evaluation; it is not the production Planner implementation.

## Run the deployed actor in MuJoCo

From a fresh clone, only a normal Python virtual environment is required:

```bash
python3 -m venv .venv-mujoco
source .venv-mujoco/bin/activate
python -m pip install -r a3_deploy/a3_deploy_example/reference/requirements.txt

# Headless contract smoke. The default config selects model_21800.
a3_deploy/a3_deploy_example/scripts/run_pingpong_sim.sh --duration 10

# Interactive window at the deployment control rate.
a3_deploy/a3_deploy_example/scripts/run_pingpong_sim.sh --view --realtime
```

The actor has two inputs (`obs[1,110]`, `time_step[1,1]`) and an
`actions[1,31]` output. The public wrapper derives the reference clock from the
current command, translates between the training and SDK joint orders, and
loads the model's exported action and PD arrays. Compact single-input public
exports remain supported through `--onnx`.

The standalone real-ball evaluator remains available for focused policy checks:

```bash
MUJOCO_GL=egl python hope_training/whole_body_tracking/scripts/mujoco_eval_onnx.py \
  --eval-mode independent --num-serves 4 --max-trial-seconds 1.8 --seed 0
```

## Gate 3 closed-loop video

The committed video was recorded from build_1's Gate 3 qualification and the
published model_21800 policy directory. It is not the standalone evaluator
above. The no-argument Gate 3 entry runs that original 12-ball qualification
with the same C++ packetizer/Planner topology as hardware:

```text
physical MuJoCo ball -> simulated OptiTrack -> production relay -> Planner
-> schema-2 command -> policy-native C++ runner -> AimRT MuJoCo plant
```

The runner entered MOTION once and was not reset between shots. Gate 3 invokes
the x86-only `--gate3-qdes-audit-only` option: finite `q_des` is published
unchanged, and `q_des` or measured actual-q limit excesses are recorded as
telemetry instead of terminating the runner. The production default is
unchanged when this explicit Gate 3 option is absent.

The video documents the complete 12-serve Gate 3 execution path. For a current
run, use the reports produced by the command below as the source of contact,
landing, robot-state and qualification results; the recorded video is a visual
runtime reference rather than a reusable verdict.

## What the current Gate 3 test validates

The formal Gate 3 entry is an x86 MuJoCo closed loop, not an Isaac replay and
not a direct `torch.load()` of the checkpoint. `model_21800.pt` is the training
artifact; deployment runs its exported actor,
`models/model_21800/policy/exported/policy.onnx`, through the native C++ Runner.
The package builder verifies that the ONNX SHA-256 matches
`params/deploy.yaml` before it permits a Gate 3 run. Loading the `.pt` directly
is covered separately by the Isaac Lab command above.

Gate 3 exercises the complete runtime chain:

```text
MuJoCo physical ball/table/racket
  -> simulated OptiTrack and production relay
  -> Planner schema-2 command
  -> model_21800 policy-native C++ Runner
  -> AimRT MuJoCo robot plant
  -> measured contact, landing, plant and Runner reports
```

The profile is build_1's original 12-ball qualification sweep. The launcher
uses the original `[-3.0, 0.0, 2.2] m/s` feed and six forehand plus six backhand
lateral positions. Each ball remains side-neutral at the launcher: the
production C++ Planner selects forehand or backhand from live geometry. The
Runner enters MOTION once and is not reset or rescued between serves.

The explicit x86-only `--gate3-qdes-audit-only` option records finite actor
commands without clipping them so policy behavior remains observable. A
non-finite final `q_des` or measured joint state still terminates the Runner.
This option is not enabled by normal hardware launchers.

## Build the current native Runner, C++ Planner and MuJoCo components

The commands in this section run on an x86_64 development laptop. They use the
`hope` distrobox because ROS 2 Jazzy is not expected to be installed on the
host. Run each block from the host shell; every block enters the distrobox
explicitly.

### 0. One-time `hope` distrobox setup on a new machine

The tested base is an x86_64 Ubuntu 24.04 host with an Ubuntu 24.04 `hope`
container. Distrobox shares the clone and the host X11/Wayland socket with the
container, so the native build can use ROS 2 Jazzy without installing ROS on
the host and `PP_VIEWER=1` can still open the MuJoCo window.

Reference: [Distrobox create](https://distrobox.it/usage/distrobox-create/)
and the official [ROS 2 Jazzy Ubuntu installation](https://docs.ros.org/en/jazzy/Installation/Alternatives/Ubuntu-Install-Binary.html).
The shared host-install fallback and the distinction between the `hope` and
`grasping` environments are summarized in
[`DISTROBOX_SETUP.md`](DISTROBOX_SETUP.md).

### 2. Build the ROS transport and C++ Planner workspace

```bash
cd "$HOME/workspace/HOPE_OPEN"
export HOPE_OPEN_ROOT="$PWD"

distrobox enter hope -- env HOPE_OPEN_ROOT="$HOPE_OPEN_ROOT" bash -lc '
  set -eo pipefail
  source /opt/ros/jazzy/setup.bash
  cd "$HOPE_OPEN_ROOT/hope_ws"

  rosdep install \
    --from-paths src \
    --ignore-src \
    --rosdistro jazzy \
    -y

  colcon build \
    --symlink-install \
    --packages-select hope_msgs hope_bringup hope_planner_cpp \
    --cmake-args \
      -DBUILD_TESTING=OFF \
      -DCMAKE_BUILD_TYPE=Release \
      -DPython3_EXECUTABLE=/usr/bin/python3 \
      -DPYTHON_EXECUTABLE=/usr/bin/python3

  source install/local_setup.bash

  test "$(ros2 pkg prefix hope_planner_cpp)" = \
    "$HOPE_OPEN_ROOT/hope_ws/install/hope_planner_cpp"
  test -x \
    install/hope_planner_cpp/lib/hope_planner_cpp/hope_planner_cpp_node
  test -x \
    install/hope_planner_cpp/lib/hope_planner_cpp/hope_ball_flight_packetizer
  ros2 launch hope_planner_cpp model21800_hardware.xml --show-args >/dev/null

  echo "C++ Planner build and launch metadata: READY"
'
```

The two executables above are the current runtime pair: the Laptop-side
`hope_ball_flight_packetizer` freezes an incoming flight into
`/ball/flight_packet`, and the HDU-side `hope_planner_cpp_node` consumes that
packet and publishes the schema-2 racket command. Do not substitute the retired
`hope_planner` package. The explicit `/usr/bin/python3` settings keep Jazzy's
rosidl message generator on Ubuntu's Python 3.12 when a user-level Python 3.10
is earlier on `PATH`; they do not make the Planner a Python runtime.

### 8. Startup troubleshooting

- `runtime config missing: .../dist/a3_deploy_x86_64/...` means the native x86
  package in step 3 has not been produced. It does not mean that the user must
  cross-compile for Rockchip.
- A missing `libaimrt_iceoryx_plugin.so` or `libaimrt_ros2_plugin.so` means the
  native package is incomplete. Re-run step 3 from a clean current checkout;
  `--pingpong-only` now builds both runtime-loaded plugin targets explicitly.
- `PREFLIGHT PASS` proves dependencies and C++ topology only. Run step 7 to
  produce contact, landing and Runner/plant measurements.
- A MuJoCo window requires a working host display socket. Confirm it with
  `distrobox enter hope -- xdpyinfo >/dev/null`; otherwise use `PP_VIEWER=0`.

## Native Runner and C++ Planner reference

The model directory already has the layout consumed by the build_1 C++ runner:

```text
models/model_21800/policy/
├── exported/policy.onnx
└── params/deploy.yaml
```

After building `a3_deploy_onnx_ref_pingpong`, select the public
transport/runtime config and pass that directory as `--policy-dir`:

```bash
cd a3_deploy/a3_deploy_example
source setup_a3_env.sh
cmake -S . -B build
cmake --build build --target a3_deploy_onnx_ref_pingpong -j

# The source-tree build writes the executable under dist/. Start in PASSIVE;
# --planner selects the schema-2 command input published by the C++ Planner.
dist/a3_deploy_x86_64/a3_deploy_onnx_ref_pingpong \
  --runtime-cfg src/a3/a3_deploy_onnx_ref/config/a3_runtime_config.pingpong.hitter_pingpong.yaml \
  --policy-dir models/model_21800/policy --planner --policy-native \
  --start passive --official-stand
```

The supported Planner process is the C++ node below. Its production input is
the immutable `/ball/flight_packet` published by
`hope_ball_flight_packetizer`:

```bash
source /opt/ros/jazzy/setup.bash
source hope_ws/install/local_setup.bash

ros2 launch hope_planner_cpp model21800_hardware.xml
```

The Planner and Runner normally execute on different machines in the hardware
topology; this command is the Planner identity reference, not an instruction to
co-locate both processes.

That is the public equivalent of the model selection in the build_1 field
procedure; site addresses, operator login details and session logs are
deliberately not published. The source Runner, C++ Planner and model bundle are
open, while actual A3 motor I/O still requires the separately licensed AgiBot
vendor runtime. Operators must retain their vendor e-stop, limits and hardware
procedure; this document does not auto-start motion or bypass robot protections.

The source and published model artifacts are released under the repository
license. AgiBot-provided files retain the notices and licensing stated in
[`A3_ASSETS.md`](../A3_ASSETS.md).
